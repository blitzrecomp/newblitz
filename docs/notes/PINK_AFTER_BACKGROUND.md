# Pink after the app switcher (iPhone, 1.0.3 build 818)

The team, 2026-11-26: mid-game on his iPhone 15 Pro he swiped up to the app switcher and came back. The game's picture was
solid magenta at first and came back after a while; the menus' panels (the Season pre-game card, Settings, every
panel) stayed bright magenta for the rest of the session, in the recording too. Log:
`build/ios_backups/20261126-bills-pink/blitz.prev.log` (main checkout), lines 367-415.

## What the log and the code show

```
[window] unfocused / size changed (852, 393) / minimized          <- willResignActive
[background] mid-game: paused, then the Auto slot
[savestate] ... saved ...
[background] the game holds
[fps] no new frame for 8 s; the VI still ticks
[rescue] no game frame for 11 s mid-game: keeping the newest Redo Play snapshot   <- the app coming back
[background] the game carries on
[status] The game stopped responding. Close New Blitz and open it again ...
[window] focused / size changed (393, 852) / restored / size changed (852, 393)  <- didBecomeActive
```

**Magenta is a texture or target the GPU never wrote.** On Metal a new texture's contents are undefined until a command
buffer writes them, and they show as magenta (the same thing rt64-patches/0002 clears for new colour targets). A command
buffer iOS refuses (an app may not submit GPU work in the background) leaves whatever it should have drawn or uploaded
that way.

**What was magenta is exactly the UI's images.** The panels are 9-slice PNG frames and corner pieces (src/main/ui_kit.cpp
`panel`); the Settings tab strip, the buttons and toggles, which are flat colours, and all the text were fine. Those PNGs
are uploaded once, by the UI renderer's own copy queue (RecompFrontend `ui_renderer.cpp` `LoadTexture`), the first time
anything draws them, and RmlUi keeps the texture for the life of the app (`FileTextureDatabase`): one upload that never
landed is magenta for the rest of the session, on every panel that shares the frame. The game's picture is redrawn every
frame, so it heals as soon as the game's frames come again: magenta at first, then fine.

**The app did GPU work in the background.** Three sources, all unguarded on iOS:

1. RT64's idle thread (`WorkloadQueue::idleThreadLoop`, user setting `idleWorkActive`, on by default) dispatches a
   compute job up to a thousand times a second whenever the GPU's otherwise idle, background or not. Only Potato Mode
   turned it off. In the background every one of those is refused.
2. The freeze rescue's false positive (below) set `blitz_replay_keep_presenting`, which makes RT64 present every VI:
   the present thread then drew the UI (and uploaded anything it hadn't drawn before) as the app came back.
3. `blitz_app_foreground` runs on willEnterForeground, while iOS still counts the app as in the background, and lets the
   game go: its frames, presents and texture uploads start before didBecomeActive.

Whichever of these left the UI's frame textures undefined (a refused upload, or uploads ignored for a while after a run
of refusals), nothing ever uploaded them again.

**The freeze rescue fired on a healthy game.** `rescue_watch` (src/game/savestate.cpp) skipped the rescue while
`in_background` or `background_hold`, but `blitz_app_foreground` clears both at once, so the next VI saw the whole 11 s
spent in the background as a stall and posted "The game stopped responding" (and the keep-presenting above). It fired
again on the trip at 297 s (6 s).

The transient portrait size on return (393x852, then 852x393 2 ms later) re-lays out the menus (patch 0044) and makes
the UI renderer park its landscape MSAA targets and make portrait ones for a frame; those are cleared every frame, and
the textures RmlUi already has aren't regenerated by a layout, so that isn't what kept the panels magenta.

## The change (branch from `1.0.4`)

- **No GPU work in the background (rt64-patches/0037-no-gpu-work-in-the-background.patch).** `blitz_rt64_gpu_away(1)`
  sets `blitz_gpu_away`; RT64's present thread, workload thread, texture upload and stream threads, and every
  `RenderWorker::execute` then wait at their next submission until `blitz_rt64_gpu_away(0)`; the idle thread does
  nothing. The thread that set it (the main thread) never waits, so it can't deadlock itself. Setting it gives work
  already under way up to 300 ms to finish (iOS wants it done before suspending the app) and logs `[gpu] background:`.
  The present thread waits before it draws anything, so the UI and its uploads wait too.
- **iOS calls it** (src/main/main.cpp, `create_gfx`, `BLITZ_IOS` only): on `SDL_APP_DIDENTERBACKGROUND`
  (didEnterBackground) after waiting up to 2 s for the game to hold (mid-game it first pauses and saves the Auto slot,
  which needs a few frames); cleared on `SDL_APP_DIDENTERFOREGROUND` (didBecomeActive). willResignActive alone (Control
  Center, a call banner) doesn't stop the GPU: iOS still allows it then. Android and the other platforms never set it.
  `[app] inactive / in the background / coming back / active` lines now go in the log.
- **The UI's textures are renewed on return (recompfrontend-patches/0045-renew-textures-after-background.patch).**
  `recompui::renew_textures()`; the next UI draw, under the UI lock and before drawing, calls `Rml::ReleaseTextures()`
  and drops the renderer's 1x1 white and transparent textures; each is uploaded again the next time it's drawn (in the
  foreground). iOS calls it on didBecomeActive after any willResignActive. Costs one re-decode of the PNGs on screen on
  return. Logs `[ui] textures dropped`.
- **The freeze rescue doesn't count the background (src/game/savestate.cpp `rescue_watch`).** While the app's in the
  background or holding, the stall so far is remembered and nothing else happens; after, only the time since it came
  back counts, until a frame comes. A game that is really stuck after coming back is still rescued, 5 s on; one that
  froze before going away is handled as before by `blitz_app_background` (it reads the same, background-free, figure).

## Remaining concerns

- **Not tried on the phone.** Built for iOS only; nothing here could run on the Mac (iOS's refusal is the trigger).
- **Which of the three sources did it is not proven.** The fix covers all three, and the renewal on return repairs
  the UI whichever it was; the new `[app]`/`[gpu]` lines will show the order of events next time.
- **The app switcher may only make the app inactive**, not background it, if the team comes back quickly; then no GPU gate
  engages (the GPU is allowed), but the renewal still runs on return.
- **A game stuck before going away and still not holding after 2 s:** RT64 then holds its work anyway; that game's
  thread waits on the GPU until the app's back (it was stuck anyway, and the rescue covers it).
- **Game textures (RT64's texture cache) aren't renewed.** Nothing showed them broken (the picture came back), and
  with the gate nothing uploads them in the background now.
- **The one-off decode on return** (the 1920x1080 backgrounds when a menu shows them) may hitch the first frame back.
